# 04-platform/emails/

Transactional email templates. React Email components that render to HTML and plain text. All outbound user-facing email (except marketing) comes from this folder.

## Files

Each email is its own file. The convention: `[event].tsx` and `[event].plain.ts` (the plain text version).

- `purchase-confirmation.tsx` — sent after a successful Stripe checkout
- `refund-confirmation.tsx` — sent after a refund is processed
- `library-access.tsx` — sent when a user is granted library access (e.g. partner gift, manual grant)
- `password-reset.tsx` — sent when the user requests a password reset
- `email-verification.tsx` — sent on signup to verify the email
- `partner-payout-sent.tsx` — sent when a PayPal payout is processed
- `partner-product-approved.tsx` — sent when an admin approves a product for publication
- `partner-product-rejected.tsx` — sent when an admin rejects a product, with the rejection reason
- `affiliate-payout-sent.tsx` — sent when an affiliate payout is processed
- `admin-new-product-pending.tsx` — sent to admins when a new product is awaiting review
- `welcome.tsx` — sent on signup, includes the welcome + license reminder
- `_components/` — shared subcomponents used by multiple emails (Header, Footer, Button)

## The stack

We use **React Email** (`@react-email/components`). Templates are React components that render to HTML. Plain text versions are auto-generated by the React Email CLI, but we override for the most-sent emails (purchase confirmation, refund) to make sure the plain text is actually good.

```tsx
// purchase-confirmation.tsx
import { Body, Container, Heading, Text, Button, Section } from '@react-email/components';
import { Header } from './_components/Header';
import { Footer } from './_components/Footer';

export function PurchaseConfirmationEmail({ order, user, product }: Props) {
  return (
    <Html>
      <Head />
      <Preview>Your purchase of {product.title} is confirmed</Preview>
      <Body style={body}>
        <Container>
          <Header />
          <Section>
            <Heading>Thanks for your purchase</Heading>
            <Text>Order #{order.number}</Text>
            <Text>You now have lifetime access to {product.title}.</Text>
            <Button href={libraryUrl}>Go to your library</Button>
          </Section>
          <Footer />
        </Container>
      </Body>
    </Html>
  );
}
```

## Sending emails

Emails are sent from server actions and webhooks via `04-platform/ci/scripts/send-email.ts` (which wraps Resend). They are NOT sent from React Server Components directly. The flow:

```ts
// In a server action (e.g. after checkout success)
import { sendEmail } from '04-platform/ci/scripts/send-email';
import { PurchaseConfirmationEmail } from '04-platform/emails/purchase-confirmation';

await sendEmail({
  to: user.email,
  subject: `Your purchase of ${product.title}`,
  react: <PurchaseConfirmationEmail order={order} user={user} product={product} />,
});
```

The `sendEmail` function:
1. Renders the React component to HTML and plain text
2. Validates the email (no broken links, no missing images)
3. Sends via Resend
4. Logs the send to `email_log` (for deliverability monitoring)
5. Returns the message ID (for tracking)

## Security rule: no file URLs in emails

**Emails must never contain signed file URLs (or any direct file/bucket URL).** Every email that gives access to purchased content links to an auth-gated page — `/library` or `/library/vault` — where the logged-in user generates their own signed URL. Why: email is the most-leaked channel we have (forwards, compromised inboxes, scrapers). A signed URL in an email is a 24h unauthenticated download link to whoever holds the message.

This applies to every template in this folder, including `library-access.tsx` and `purchase-confirmation.tsx` (the "Go to your library" button is correct: it points to a page, not a file). The reviewer blocks any email PR that embeds a `b-cdn.net`, storage-zone, or otherwise signed URL. Audited in `06-quality/checklists/security-audit.md`.

## Template design rules

- **Branding consistent with the app.** Same fonts, same colors, same header/footer.
- **Plain text version always.** Many of our users read email on text-only clients.
- **No images in the first viewport.** Images can be blocked; the message must work without them.
- **Single column, max 600px wide.** Standard email width.
- **Dark mode supported.** Resend's email client tests with both modes; templates render in both.
- **No web fonts.** Use system fonts only (web fonts are blocked in many email clients).
- **Unsubscribe link in every email.** Required by CAN-SPAM. For transactional emails, the unsubscribe is "manage notifications" (not "stop all email").

## When to add a new email

1. A new user-facing event happens (e.g. "your affiliate link got 10 clicks today")
2. A new transactional flow is added (e.g. "we received your refund request")
3. An existing flow needs a new email (e.g. "your payout failed, please update your PayPal email")

To add a new email:
1. Create the `.tsx` file in this folder
2. Create the `.plain.ts` file (if the plain text needs custom treatment)
3. Add a `sendEmail(...)` call in the relevant server action or webhook
4. Update the relevant spec to mention the email
5. Test in staging with mail-tester.com to verify deliverability

## Preview and test

```bash
# Preview all emails in a dev server
pnpm email:dev

# Send a test email to your inbox
pnpm email:test purchase-confirmation --to your@email.com
```

The dev server uses React Email's built-in preview, which shows the template with mock props.

## What does NOT go here

- Marketing emails (newsletters, product announcements) — those go through a separate system (Resend Audiences or a third-party like ConvertKit)
- Push notifications — those are a separate system
- Slack messages to the team — those are a separate system
- In-app toasts — those are React components, not emails

If the message goes to a user's inbox, it's an email. If it goes to their browser tab, it's a toast. If it goes to our team Slack, it's a notification.
