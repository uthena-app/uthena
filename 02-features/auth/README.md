# Feature: auth

Login, signup, password reset, email verification, OAuth callback. Wraps Supabase Auth; session helpers live in `00-foundations/auth/`, this feature owns the user-facing flows.

- **Specs:** `01-specs/pages/login.md`, `signup.md`, `reset-password.md`, `update-password.md`, `verify-email.md`, `account-password.md`, `auth-callback.md`
- **Owner:** Mavis (cron-driven, one slice per tick)
- **Depends on:** `00-foundations/auth`, `00-foundations/data`, `00-foundations/log`, `00-foundations/ui`
- **Depended on by:** every other feature (session + role checks)
- **Status:** Phase 1 in progress. **P1.1 (signup UX) + P1.2 (login UX) + P1.3 (password reset UX) + P1.4 (change password logged-in) + P1.5 (email verification UX) shipped.** Signup has terms checkbox + `?next=` pass-through + password strength meter + audit logging + verify gate. Login has `?next=` pass-through + remember-me + inline rate-limit cooldown + audit logging + already-logged-in redirect + every-failure audit row. Password reset is two-step (request link → set new) with enumeration protection (constant-time delay + same "Check your email" panel for any outcome), per-kind rate limits (3/email + 10/IP for request, 5/email + 20/IP for update), `?next=` pass-through through the email round-trip, password strength meter on the set-new form, "expired/wrong/already-used" unified state, brief success state before redirect. Change-password-while-logged-in re-uses the same rate-limit + schema as P1.3's reset-completion flow but adds current-password verification via the service-role Supabase client (so the user's existing session is not replaced) and an OAuth-only-user short-circuit. Email verification handles all four entry shapes (direct OTP-style `?token_hash=...&type=email`, post-callback `?type=signup`, no-token + signed-in, no-token + anonymous) with success auto-redirect after 2s + expired state with rate-limited resend form (1/email/15min + 20/IP/15min) + audit-logged resend action + unified "check your inbox" landing for the no-token branches.

## File map

- **`AuthForms.tsx`** — client components: `SignInForm`, `SignUpForm`, `ResetPasswordForm`. `UpdatePasswordForm.tsx`, `ChangePasswordForm.tsx`, and `ResendVerificationForm.tsx` are split out (separate routes, separate concerns). **P1.3:** `ResetPasswordForm` accepts `next` and renders a real "Check your email" confirmation panel that replaces the form post-submit (with the echoed email + "Try again" button); the form has a hidden honeypot like SignUpForm.
- **`passwordStrength.ts`** — shared pure helper extracted from `AuthForms.tsx` (P1.3) so `SignUpForm`, `UpdatePasswordForm`, and `ChangePasswordForm` can all import it. 5-bar meter logic (length + variety + 14-char floor for "strong").
- **`AuthForms.module.css`** — token-only styles. P1.1 added: `.checkboxRow`, `.checkbox`, `.strengthMeter` + `.strengthBar` + `.strengthBarOn_{0..4}` + `.strengthLabel`, `.fieldError`, `.serverMessageHint`. P1.2 added: `.rememberRow`, `.cooldownNotice` + `.cooldownLabel` + `.cooldownCount` + `.cooldownHint`. P1.3 added: `.emailEcho` (mono-font chip for the confirmation panel) + `.tryAgainButton` (secondary "Try again" CTA on the confirmation panel). **P1.4:** no new classes — the change-password form reuses the existing `.form` / `.h1` / `.lede` / `.serverError` / `.cooldownNotice` / `.strengthMeter` shapes for visual consistency.
- **`actions.ts`** — server actions (`'use server'`):
  - `signUpAction(formData)` — accepts `next`, `acceptTerms` (Zod-validated as `z.literal(true)`). Re-validates `next` via the `safeNext()` open-redirect guard. Writes one `admin_audit_log` row per SUCCESSFUL signup (failed attempts stay at pino warn level — FK on `actor_id` requires an existing `auth.users.id`). Returns the `AuthActionResult` discriminated union so the form can render inline errors.
  - `signInAction(formData)` (P1.2) — accepts `next`, `remember` (UI hint only). Calls `checkRateLimit()` BEFORE the Supabase Auth call; on lockout, returns `{ ok: false, rateLimited: { retryAfterSeconds, dimension: 'email'|'ip' } }`. On every failure, calls `recordAuthFailure()` with `mapFailureReason()`. On lockout, calls `auditRateLimitTrigger()` with `action='signin_rate_limited'`.
  - **`requestPasswordResetAction(formData)` (P1.3)** — accepts `next` (embedded in the email's `redirectTo` for the post-reset flow). Calls `checkRateLimit({ kind: 'reset_password', ... })` BEFORE the Supabase call. On lockout, returns the SAME generic `{ ok: true, message: 'If an account exists...', emailEcho }` (no cooldown UI; the rate-limit path is invisible to the user per the spec's enumeration hardening requirement). On every lockout, calls `recordAuthFailure()` + `auditRateLimitTrigger({ kind: 'reset_password', ... })` with `action='password_reset_rate_limited'`. Pads the response to `RESET_MIN_RESPONSE_MS = 500` so the "email exists" vs "doesn't exist" branches are indistinguishable to a timing oracle.
  - **`updatePasswordAction(formData)` (P1.3)** — accepts `next` (post-update destination). Schema is stricter than signup: `min(12)` + digit + symbol (vs signup's `min(10)` + upper/lower/digit). Reads the authenticated user from the session (the reset-token session has a known email via `auth.users.email`); returns `{ ok: false, error: 'Your reset link has expired...' }` if no session. Calls `checkRateLimit({ kind: 'update_password', ... })` BEFORE the Supabase call; on lockout, returns `rateLimited` and the form surfaces the cooldown inline (this surface is NOT enumeration-sensitive — the user already proved inbox access, so a cooldown is fine). On every failure, calls `recordAuthFailure()`. On lockout, calls `auditRateLimitTrigger({ kind: 'update_password', ... })` with `action='password_update_rate_limited'`. Successful updates are NOT individually audited (volume).
  - **`changePasswordAction(formData)` (P1.4)** — accepts `currentPassword`, `password`, `confirm`. The verify-current-password step uses the **service-role** Supabase client (`getServiceSupabase()` — `auth: { persistSession: false }`) so the user's existing session cookies are NOT replaced by the verify call. The flow: (1) Zod-validate; (2) `getUser()` to read the session; (3) if no session → "Your session has expired. Sign in again."; (4) `getUserIdentities()` to detect OAuth-only users → friendly "use reset flow" message WITHOUT a probe attempt; (5) `signInWithPassword` via service-role → if it fails → "Current password is incorrect." + record failure; (6) check new != current → "New password must differ..."; (7) `checkRateLimit({ kind: 'update_password', ... })` (re-uses the P1.3 bucket — one policy across reset-completion + logged-in change); (8) `updateUser({ password })` on the request session; (9) `revalidatePath('/', 'layout')` + return success. The user STAYS signed in on the same session; only the password is rotated.
  - **`resendVerificationEmailAction(formData)` (P1.5)** — accepts an empty FormData (the email is read from the session, not from the form). The flow: (1) Zod-validate the empty payload; (2) `getUser()` to read the session; (3) if no session → "Sign in to resend"; (4) if `email_confirmed_at` is set → "Your email is already verified" (no email sent); (5) `checkRateLimit({ kind: 'email_verification', ... })` — 1/email/15min + 20/IP/15min (satisfies spec's "1 per 60s + 5 per hour" intent); (6) on lockout, returns `rateLimited` with the precise retry-after; (7) `supabase.auth.resend({ type: 'signup', email, options: { emailRedirectTo: /auth/callback?next=/verify-email?type=signup } })`; (8) on success, writes one `admin_audit_log` row with `action='email_verification_resent'` so admins can see the volume (the action's FK points at the real user, not the pre-auth system hack used by rate-limit triggers).
  - `signOutAction()` — clears the session cookie + redirects to `/`.
  - `safeNext(raw)` — re-exported from `00-foundations/auth/safe-next.ts` (P2.1 lifted the helper from this feature's `redirect.ts` to the foundations layer because it's used by 6+ callers across the codebase and the guards layer shouldn't depend on a feature). Returns a sanitized relative path or `null`. Rules: must start with `/`, must NOT start with `//`, must NOT contain `\`, must NOT be `/:something://`, must NOT contain `%2f%2f`.
- **`UpdatePasswordForm.tsx`** — dedicated client form for the post-reset flow. **P1.3:** accepts `next`; renders a live password strength meter (same helper as SignUpForm); submit is `disabled + aria-disabled` until `canSubmit` is true (both fields non-empty + match + score ≥ 2); renders a brief "Password updated — Redirecting to your library…" state for 1.2s before the action's `redirectTo` fires; schema is `min(12)` + digit + symbol.
- **`ChangePasswordForm.tsx` (P1.4)** — dedicated client form for the logged-in change flow at `/account/password`. Three fields (current / new / confirm) + live strength meter + rate-limit cooldown (same shape as the login form's cooldown). Submit disabled until all three fields are non-empty AND new = confirm AND strength score ≥ 2. On wrong-current-password: resets the current-password field only (so the user doesn't re-type the new password); on success: 1.2s "Password updated" state then `router.push('/account/profile')`.
- **`ResendVerificationForm.tsx` (P1.5)** — dedicated client island for the verify-email resend flow. Single button "Resend verification email" with live cooldown countdown ("Try again in Xm Ys") when the server returns a rate-limited verdict, success toast ("Check your inbox for the new link.") for 4s on success, inline error message on failure. The button is the only client JS shipped on the verify-email expired branch; the rest of the page stays RSC.
- **`VerifyEmailRedirect.tsx` (P1.5)** — tiny client island that handles the 2s auto-redirect after a successful verification. Mounted only on the success branch; returns `null`. Honors `prefers-reduced-motion` by skipping the auto-redirect (the user can still use the "Go to your library" link).
- **`callbackRateLimit.ts` (P1.9)** — per-IP rate limiting + suspicious-pattern detection for the auth callback. Separate module from `00-foundations/auth/rate-limit.ts` because the callback needs TWO windows (5min + 1h) instead of one, and records both successes and failures (the existing helper is failure-only). Public surface: `recordCallbackHit({ ip, userAgent, reason })` writes one `auth_failed_attempts` row (kind='oauth_callback'); `checkCallbackRateLimit({ ip })` returns the verdict for the tighter window; `countRecentCallbackSuccesses({ ip })` returns the suspicious-pattern count; `auditCallbackEvent({ action, ip, userAgent, count, metadata })` writes the `oauth_callback_rate_limited` / `oauth_suspicious_activity` rows to `admin_audit_log`. Fails open on any DB error (consistent with the existing rate-limit helper's policy).
- **`redirect.ts`** — *removed in P2.1*. The `safeNext()` helper was lifted to `00-foundations/auth/safe-next.ts` because it's a pure helper used by 6+ callers and the auth-guard layer shouldn't depend on a feature.

## Rate-limit infrastructure

- **`00-foundations/auth/rate-limit.ts`** — DB-backed sliding-window rate limiter. **P1.3** extended the helper from P1.2's signin-only to support four kinds. **P1.5** adds the fifth:
  - `signin` — 5/email/15min + 20/IP/15min. Action: `signin_rate_limited`.
  - `signup` — 3/email/15min + 10/IP/15min (reserved; signup action adopts in PH2). Action: `signup_rate_limited`.
  - `reset_password` — 3/email/15min + 10/IP/15min. Action: `password_reset_rate_limited`.
  - `update_password` — 5/email/15min + 20/IP/15min. Action: `password_update_rate_limited`.
  - `email_verification` — 1/email/15min + 20/IP/15min (satisfies spec's "1 per 60s + 5 per hour" intent with the single-window shape). Action: `email_verification_rate_limited`.
  Public surface (unchanged shape; the kind parameter dispatches to the right limit):
  - `checkRateLimit({ kind, email, ip })` — returns `{ allowed, retryAfterSeconds, triggered, count }`. **P1.3 fail-open:** if `getServiceSupabase()` throws, returns `{ allowed: true, retryAfterSeconds: 0 }` and logs `rate_limit_supabase_unavailable` (so a local-dev DB outage doesn't take down the auth flow).
  - `recordAuthFailure({ kind, email, ip, userAgent, reason })` — INSERTs one row. Reasons: `invalid_credentials | rate_limited | email_not_verified | unknown_user | malformed_input | server_error`.
  - `retryAfterSeconds({ kind, email, ip, dimension })` — recomputes the precise remaining seconds from the most-recent attempt in the window.
  - `auditRateLimitTrigger({ kind, email, ip, userAgent, dimension, count })` — writes one `admin_audit_log` row per trigger event. The action name is looked up from `AUDIT_ACTION_BY_KIND` (each kind maps to its own spec-required action).
  - Lazy GC (every 32nd call) deletes rows older than 24h.
- **`04-platform/migrations/0017_auth_failed_attempts.sql`** — the counter table (P1.2).
- **`04-platform/migrations/0018_auth_failed_attempts_extend.sql`** — P1.3 extends the `kind` check constraint to include `update_password`. The DO block reads the auto-generated constraint name from `pg_constraint` and drops it by OID (defensive against PG version differences in inline check-constraint naming).
- **`04-platform/migrations/0019_auth_failed_attempts_email_verification.sql`** — P1.5 extends the `kind` check constraint to include `email_verification`. Same DO-block / pg_constraint scan pattern as 0018.
- **`04-platform/migrations/0020_auth_failed_attempts_oauth_signin.sql`** — P1.6 extends the `kind` check constraint to include `oauth_signin`. Same DO-block pattern.
- **`04-platform/migrations/0022_auth_failed_attempts_oauth_callback.sql`** — P1.9 extends the `kind` check constraint to include `oauth_callback` AND the `reason` check constraint to include `success` (so the suspicious-pattern detector can count successful flows). Two DO blocks (one per enum), same defensive pattern as the prior migrations.

- **STUB-041** — Fine-grained "1 per 60s + 5 per hour" window split for the email-verification resend. The current `checkRateLimit` helper uses a single 15-min window; the action uses `perEmail: 1` which gives max 4 attempts per hour (strictly tighter than the spec's "5 per hour" floor and far exceeds "1 per 60s"). If real-world abuse shows the gap matters, the helper gains a `windowSeconds` override so the 60s and 60min windows can coexist.
