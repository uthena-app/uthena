# Affiliate Onboarding — `/affiliate/onboarding`

## What this page does

A 6-step wizard that turns a logged-in customer into a pending affiliate. Steps render in order with a stepper at the top showing progress: **Welcome → Handle & bio → Payout → Promo methods → Agreement → Submit**. Users can save & exit at any step and resume from the same step later. Each step validates its own data before the user advances; "Next" stays disabled until the step is valid. A persistent "Progress saved" toast confirms each successful step save.

The handle is reserved on step 2 (server-side uniqueness check) and held in the draft. On final submit, an `affiliates` row is created with `status = 'pending'`, the `affiliate_onboarding_drafts` row is marked `submitted_at`, a confirmation email is queued, and an admin alert is queued. The user lands on a "Thanks, we'll review within 2 business days" screen. Once an admin approves, the user is moved to `status = 'approved'`, gets an approval email, and the next visit to `/affiliate/onboarding` redirects to `/affiliate`.

The handle is a critical field — it appears in the public mini-shop URL `uthena.com/[handle]`. Uniqueness is enforced at the draft level (to reserve it during the wizard) and again at submit (to prevent a race where two users both picked the same handle in step 2). See Security.

Migration requirement: the current affiliate program entry point is `affiliate.uthena.com/register`. After DNS cutover, that URL must route into this onboarding flow and preserve only safe attribution params.

## Data this page shows

| Step | Field | Source | Format | Validation |
|---|---|---|---|---|
| (header) | `profiles.display_name`, `profiles.avatar_url`, current step, total steps, "Resume" / "Start over" controls | `affiliate_onboarding_drafts` join `profiles` | stepper + avatar | — |
| 1. Welcome | Hard-coded copy: 20% commission, 30-day cookie window, payment terms, "What you'll need" checklist | static | text + checklist | — |
| 2. Handle & bio | `handle` (required, 3-30 chars, lowercase letters/digits/hyphens, must be unique), `bio` (max 280 chars, optional), `avatar` upload (jpg/png, max 2MB) — pre-filled from `profiles` if set | `profiles` + draft | form | Zod: `handle` matches `^[a-z0-9-]{3,30}$`, not in a reserved list (`admin`, `api`, `app`, `help`, `support`, `uthena`, `library`, `browse`, `collections`, `products`, `partner`, `affiliate`, `login`, `signup`, `settings`, `account`), unique against `affiliates.handle` AND `affiliate_onboarding_drafts (jsonb → handle)`. Server-side uniqueness check via a single `INSERT ... ON CONFLICT` against a `handle_reservations` table OR a CTE race-safe check. |
| 3. Payout | `paypal_email` (required), `paypal_email_confirm` (must match) | draft | form | Zod: RFC-5322 email, identical to confirm. Note: $50 minimum payout threshold — referenced in the copy, enforced in `/admin/payouts` (not in v1: in the affiliate dashboard only). |
| 4. Promo methods | `promo_methods` (multi-select: `twitter`, `youtube`, `blog`, `email_list`, `tiktok`, `linkedin`, `other`); optional `other_text` | draft | checkboxes | At least one optional — no enforcement, all checkboxes may be unchecked (this step is purely informational) |
| 5. Agreement | `affiliate_terms_accepted` (bool), `tos_accepted` (bool) | draft | checkboxes | both must be true to enable Submit |
| 6. Submit | Summary view (read-only): handle, bio, payout email (masked: `j***@paypal.com`), promo methods, "Submit application" button | draft | summary | — |

**Server actions** in `02-features/affiliate-portal/actions/onboarding/`:
- `saveStep(userId, step, payload)` — upserts the draft. For step 2, performs the handle uniqueness check (see Security). Returns `{ ok, savedAt, handleConflict?: true }`.
- `checkHandleAvailability(handle)` — preview-only check the user can run from the handle field as they type. Returns `{ available: boolean, suggestion?: string }` (suggestion is generated by appending 2-4 random digits to a slugified version of the requested handle, e.g. `marcus-reyes-482`). Debounced 300ms client-side; 5/sec rate limit server-side.
- `submitApplication(userId)` — atomic. Inserts `affiliates` row with `status='pending'`, copies fields from draft, marks draft `submitted_at = now()`, enqueues 2 emails. Idempotent: re-submit on a `pending`/`approved` application returns `{ ok: true, alreadySubmitted: true }` and does NOT create a duplicate row.

**Storage:** avatar uploads go to Bunny Storage under `onboarding/affiliate/{userId}/avatar/{uuid}.{ext}`. No other files in v1.

| Action | Trigger | Result | RBAC |
|---|---|---|---|
| Open onboarding | Direct nav to `/affiliate/onboarding` while logged in | Render the step the user is on (or step 1 if no draft) | authenticated user, role ≠ affiliate (existing affiliates get redirect to `/affiliate`) |

| Check handle availability | Type in the handle field (debounced 300ms) | Calls `checkHandleAvailability`; shows ✓/✗ and an optional suggested alternative | authenticated |
| Reserve handle | Click "Next" on step 2 | Race-safe `INSERT INTO handle_reservations` inside `saveStep`; if conflict, return `{ handleConflict: true }` and the UI keeps the user on step 2 with an error | authenticated, draft owner |

| Restart onboarding | Click "Start over" on step 1 or higher | Confirmation modal, then `DELETE FROM affiliate_onboarding_drafts WHERE user_id = self` AND `DELETE FROM handle_reservations WHERE user_id = self AND draft_id = self` (releases the handle) | authenticated |
| Submit application | Click "Submit application" on step 6 | Atomic: insert `affiliates` row (with the reserved handle), mark draft `submitted_at`, release the reservation (the handle now lives on `affiliates.handle`), queue 2 emails, navigate to `/affiliate/onboarding/thanks` | authenticated, draft owner, no existing `affiliates` row OR existing row is `status = 'suspended'` |
| Re-submit (idempotency) | Click "Submit" again with the same draft | Returns `{ ok: true, alreadySubmitted: true }`; UI shows "Submitted" state, no duplicate row created | authenticated |
| Exit | Click "Exit" / browser close | Draft is auto-saved on each step; the handle reservation stays in place; user resumes by returning to `/affiliate/onboarding` | — |
| View terms | Click "Read the Affiliate Terms" link | Opens PDF in a modal or new tab (PDF lives in `04-platform/emails/legal/affiliate-terms.pdf`) | authenticated |

- No KYC or tax form collection in v1 (affiliates are 1099-NEC recipients in the US; tax form collection is triggered at first payout over the IRS threshold, not at onboarding — see `/admin/payouts` spec)
- No tracking pixel / postback URL setup (the `?ref=` cookie is enough in v1)
- No "promo code generator" (the handle is the code)
- No real-time status of admin review (email only in v1; v2 adds an in-app "Application status" page)
- No A/B test of wizard copy
- No multi-language support for the agreement PDFs (English only in v1)
- No CAPTCHA — see Open Questions
- No "Apply as a team" / sub-affiliate structure
- No "import from another affiliate network" (e.g. ShareASale) — v2
- No editing of an approved affiliate's handle post-approval (handle is locked after `status = 'approved'`; display name + bio can be edited in `/affiliate/settings` in v2)

## Security

- **Auth required:** YES — redirects anon to `/signup?next=/affiliate/onboarding`
- **Allowed roles:** any authenticated user without an active `affiliates` row (or with `status = 'suspended'` for re-submission)
- **RLS policies that apply:**
  - `affiliate_onboarding_drafts` — `select/insert/update/delete` only when `user_id = auth.uid()`
  - `affiliates` — self can `select` own row; `insert` blocked at RLS (only the `submitApplication` server action with `service_role` may insert, after Zod validation and handle transfer)
  - `handle_reservations` — self can `select/insert/delete` own row; `insert` is race-safe via a `unique (handle)` index with `INSERT ... ON CONFLICT DO NOTHING RETURNING *`
  - `profiles` — self `update` on `display_name`/`bio`/`avatar_url` only; `user_id` matches auth
  - `file_downloads` — INSERTs a row when any uploaded file is later read by an admin
- **PII displayed:** yes — user's own PayPal email (behind auth, owned by self); the handle is intentionally public
- **PII in URLs:** NO. The route is `/affiliate/onboarding`; the `user_id` is derived from the auth session server-side, never query-stringed. Step navigation uses a `?step=N` query param only (N is an integer, no PII).
- **File upload security:**
  - MIME + size validated server-side
  - Storage paths are `onboarding/affiliate/{userId}/avatar/{uuid}.{ext}` — no filename collision, no path traversal
  - Bunny Storage zone: `private`; reads require signed URLs
  - Virus scan deferred to v2 (no executable types accepted in v1 — only images)
- **Idempotency:** `submitApplication` is idempotent. The first call creates the `affiliates` row; subsequent calls on the same `user_id` return the existing row with `alreadySubmitted: true`. Implemented with a unique partial index on `affiliates(user_id) where status in ('pending', 'approved')` and an `on conflict do nothing` clause in the insert.
- **Handle uniqueness — race condition handling:** Two approaches considered:
  - **A. Reservation table** (recommended): `handle_reservations(handle text unique, user_id uuid, draft_id bigint, created_at)`. The wizard's step-2 save atomically `INSERT ... ON CONFLICT DO NOTHING`. If the row inserts, the handle is held; if not, the user gets a conflict. On submit success, the reservation is moved to `affiliates.handle` (still under the same unique index). On draft restart or 7-day timeout, the reservation is deleted. This is the approach in this spec.
  - **B. Single-stage check on submit**: user picks handle in step 2 (stored in draft, no uniqueness check), and submitApplication re-checks uniqueness. If conflict, user is sent back to step 2. Simpler but worse UX (user invests time in the wizard only to be told at submit that the handle is taken).
  - Chose A. The reservation table is small (at most a few thousand rows of in-flight wizards at any time) and the Janitor job can clean stale rows.
- **Rate limiting:** `saveStep` 60/min/user; `checkHandleAvailability` 5/sec/user; `submitApplication` 5/hour/user.
- **Audit logged:** yes — every step save, every handle reservation/release, every submit, every restart. Events: `affiliate_onboarding.step_saved`, `affiliate_onboarding.handle_reserved`, `affiliate_onboarding.handle_released`, `affiliate_onboarding.submitted`, `affiliate_onboarding.restarted`. Written to `admin_audit_log` via the `service_role` server action.
- **CSRF:** server actions protected by Next.js's built-in action token.
- **Open redirect protection:** the `?next=` param on signup is validated (must be a relative path starting with `/` and not `//`).
- **Legacy redirect safety:** legacy affiliate redirects use fixed relative targets. Only allowlisted attribution params are carried forward.
- **Session security:** see `/login` spec.
- **Third-party scripts:** none. Resend (email) and Bunny (storage) are server-side only.

## Performance

- **Target p95:** < 500ms per step navigation; < 100ms for the handle availability check (single indexed lookup); < 2s for the initial step load
- **Render strategy:** RSC + SSR for the wizard shell; client components for the form fields, stepper, and the debounced handle-availability check
- **Cache:** none — every step is user-specific. The handle availability check is NOT cached (we need the live result to avoid races).
- **DB indexes:** `affiliate_onboarding_drafts (user_id, updated_at desc)`; `handle_reservations (handle) unique`; `handle_reservations (created_at) where user_id is not null`; existing `affiliates (user_id) unique` and `affiliates (handle) unique`
- **Bundle size budget:** < 50KB added to the client bundle (form, handle input, file dropzone, stepper, validation libs)

   ```sql
   );

   create table affiliate_onboarding_drafts (
     id bigserial primary key,

     created_at timestamptz not null default now(),
     updated_at timestamptz not null default now()
   );

   create index on affiliate_onboarding_drafts (user_id) where submitted_at is null;
   -- submitted drafts kept for 90 days for audit, then janitor deletes

   alter table affiliate_onboarding_drafts enable row level security;
   create policy "affiliate_drafts_self_all" on affiliate_onboarding_drafts
     for all using (user_id = auth.uid()) with check (user_id = auth.uid());

   -- Handle reservations: a wizard holds a handle from step 2 onward
   -- (or from the moment the user passes inline availability check, whichever is later).
   create table handle_reservations (
     handle text primary key,                            -- the reserved handle, lowercased
     user_id uuid not null references auth.users(id) on delete cascade,
     draft_id bigint not null references affiliate_onboarding_drafts(id) on delete cascade,
     created_at timestamptz not null default now()
   );

   create index on handle_reservations (user_id);
   create index on handle_reservations (created_at);    -- for janitor: drop reservations older than 7 days

   alter table handle_reservations enable row level security;
   create policy "handle_reservations_self_all" on handle_reservations
     for all using (user_id = auth.uid()) with check (user_id = auth.uid());
   -- Race-safety: a unique constraint on (handle) does the heavy lifting;
   -- INSERT ... ON CONFLICT DO NOTHING is the only allowed insert pattern.
   ```

   Confirm the table names, the `jsonb`-per-step shape (vs one big `payload jsonb`), the 7-day reservation TTL, and the reserved-handle list. The reserved list is in the spec body (`admin`, `api`, `app`, etc.) — flag for review.

My recommendation: **yes**, with the same caveat as partners — drop the `affiliates.user_id unique` constraint OR archive the suspended row to `affiliates_archive`. Flag for human review — small data-model change.

Handle changes break every existing link, QR code, and saved share. If the user really needs a new handle, they re-onboard as a new affiliate (admin decides). Confirm.
