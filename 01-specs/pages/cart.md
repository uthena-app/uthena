# Cart — `/cart`

## What this page does

The buyer's pre-checkout staging area. Lists every line item the buyer has added (product thumbnail, title, license tier dropdown, unit price), shows the running subtotal, and offers two ways out: **Continue to checkout** (primary CTA → `/checkout`, requires auth) and **Continue shopping** (secondary → `/browse`). Supports both authenticated buyers (cart persisted in the `cart_items` table) and anonymous browsers (cart held in a signed `uthena_anon_cart` cookie). Authenticated users see a one-line "Your cart is saved to your account" reassurance; anonymous users see the cookie-backed cart rendered identically — the page no longer distinguishes the two paths in the UI.

This page is the single source of truth for "what is in my cart right now" across the site. The product page's "Add to cart" button, the catalog's quick-add card, and the home page's CTA all funnel here for review.

## Data this page shows

| Section | Field | Source | Format |
|---|---|---|---|
| Header | Cart title, item count | `cart_items` count (auth) or anon-cookie line count (anon) | text |
| Per-line | `product.title`, `product.slug`, `product.thumbnail_url` | `cart_items` JOIN `products` (auth) OR `products` joined live from anon-cookie product_ids | row, click thumbnail → `/products/[slug]` |
| Per-line | `tier` (Whitelabel / PLR / PLR+MRR) | `cart_items.tier` (auth) OR anon-cookie `l` (anon) | dropdown (editable) |
| Per-line | `unit_price_cents` for current tier | `product_pricing` (active, joined live so price changes propagate) | money |
| Per-line | Remove button | per-line action | icon |
| Subtotal | sum of `unit_price_cents` across lines | computed server-side | money, large |
| Subtotal | "Tax calculated at checkout" note | hard-coded | muted small text |
| Empty state | illustration, "Your cart is empty" | hard-coded | centered card with "Browse catalog" CTA |
| Trust strip | "14-day return rights", "Secure checkout", "Instant download" | hard-coded | icons + text, below subtotal |

**Queries / actions:**
- `getCart()` in `02-features/cart/queries/getCart.ts` — returns normalized `CartLine[]`. Auth branch reads `cart_items` joined live against `product_pricing`; anon branch reads the cookie via `resolveAnonCart()` and joins live against the same `product_pricing` (so price changes propagate for both).
- `addToCartAction(productId, license, quantity)` — server action. Upserts `cart_items` for auth users, writes the HMAC-signed cookie for anon.
- `updateLicenseAction(cartItemId, license)` — server action. Updates `cart_items.tier` (auth) or rewrites the cookie line (anon).
- `updateQuantityAction(cartItemId, quantity)` — server action. Same shape.
- `removeLineAction(cartItemId)` — server action. Same shape. `cartItemId` is `number` for auth or `string` (`anon:<product_id>:<license>`) for anon.
- `clearCartAction()` — server action. Soft-deletes via `status='abandoned'` (auth) or empties the cookie (anon).
- `mergeAnonCartIntoAuth(userId)` — server action. Called by `signInAction` + `signUpAction`. Union of the anon cookie + auth cart, respecting `(product_id, license)` uniqueness.
- `getCartCount()` — server component helper for the nav badge. Auth uses `get_cart_quantity_sum` RPC; anon sums quantities in JS from the cookie.
- `getCartSubtotalCents()` — server component helper. Same branching.

## User actions

| Action | Trigger | Result | RBAC |
|---|---|---|---|
| Add to cart | From product page or catalog card (calls `addToCartAction`) | Line inserted/upserted, nav badge increments, drawer slides in (P4.1) | public CTA, action works for anon (cookie) and auth (DB) |
| Change license | Pick a new value in the per-line license dropdown | `updateLicenseAction` runs, price re-renders inline | public (works for both auth and anon) |
| Remove item | Click ✕ on a line | Line removed, subtotal recomputes, count decrements | public |
| Clear cart | Click "Clear cart" link, confirm in modal | All items removed | public |
| Apply coupon | (n/a on this page — coupon is entered on `/checkout`; here we link to it) | — | — |
| Continue shopping | Click secondary link | Navigate to `/browse` | public |
| Continue to checkout | Click primary CTA | If auth: navigate to `/checkout`. If anon: navigate to `/login?next=/checkout` | public CTA, checkout requires auth |
| Sign in to save cart (anon) | (resolved by P4.2 — no longer a separate banner; the cookie is the persistent cart until signup) | — | — |

## What this page does NOT do

- No quantity selector (PLR is per-license, quantity is always 1; see `checkout.md` "What this page does NOT do")
- No coupon entry (coupon is on `/checkout` to keep the cart page purely about line items)
- No saved payment methods, no BNPL, no crypto (v2)
- No "save for later" / wishlist (v2)
- No order bumps / cross-sell (v2)
- No tax line (tax is calculated in checkout by Stripe Tax)
- No multi-currency selector (USD only in v1)
- No bulk actions on the cart (e.g. "remove all PLR") — out of scope v1
- No explicit "Keep both / Use account cart / Use session cart" merge modal on signup — the anon-to-auth merge is automatic (union, auth wins on collisions). The modal is a follow-up; see `01-specs/pages/_followups.md`.

## Security

- **Auth required:** NO — page is public; anon sees a cookie cart, auth sees a DB cart.
- **Allowed roles:** anyone (anon or auth); the route handler branches on session.
- **RLS policies that apply (auth branch):** `cart_items` (self-only for SELECT/INSERT/UPDATE/DELETE — owner matches `auth.uid()`; anon users bypass the table entirely and use the cookie). `products` (public read on `status='published'`). `product_pricing` (public read on `active = true` and product published).
- **Anon cookie (anon branch):** `uthena_anon_cart` is `HttpOnly` + `SameSite=Lax` + `Secure` (in production) + 30-day TTL. Signed with HMAC-SHA256 using `ANON_CART_SECRET` (Doppler in production, per-process in dev). Defense in depth: a Zod schema rejects corrupted cookies (bad version, bad license, qty out of range, > 50 lines) at parse time.
- **PII displayed:** no — cart items are products, not user data.
- **PII in URLs:** no — `/cart` is a static path; line items identified by `cart_items.id` (bigint, auth) or `anon:<product_id>:<license>` (anon, internal) and never appear in the URL.
- **Audit logged:** no — adding to cart isn't currently audit-logged (per `cart-drawer.md` "Routine add-to-cart events are NOT logged to keep the table small"). The merge-on-signup event is logged at info level via pino (`mergeAnonCart ok` with `sourceCount`, `mergedCount`, `skippedExisting`, `skippedUnavailable`).
- **CSRF:** server actions are CSRF-protected via Supabase auth session + same-site `Lax` cookies.
- **Abuse protection:** rate-limit add-to-cart is deferred to P18.8 (per the existing STUB; not in this tick). The cookie is HMAC-signed but not encrypted — an attacker who can read the cookie already knows the user's cart (no PII is stored). The HMAC prevents tampering; the Zod schema prevents a corrupted cookie from leaking into the rest of the app.

## Performance

- **Target p95:** < 200ms (per `docs/ARCHITECTURE.md` §5)
- **Render strategy:** RSC for the page shell + server actions for mutations. Auth cart is read in the RSC; anon cart is hydrated from the `uthena_anon_cart` cookie server-side + live-priced.
- **Cache:** none for either branch (user-specific + cookie-specific). `Cache-Control: private, no-store` on `/api/cart`.
- **DB load (auth):** one index lookup on `cart_items (user_id, status)` + one join to `products` + `product_pricing` for live pricing.
- **DB load (anon):** one PostgREST read for product + pricing across the cookie's product ids (capped at 50 ids). The cookie itself is ~1 KB; the deduped product-id list is the smaller of the two.
- **Bundle size budget:** < 20KB added to client bundle (just the dropdown + confirm-dialog interactivity).

## Out of scope for v1

- Quantity > 1 (always 1; PLR is per-license)
- Saved-for-later / wishlist
- Multi-currency display
- Cart sharing ("send this cart to a friend")
- Recently-viewed sidebar
- Cross-sell "frequently bought together"
- Cart abandonment email (Resend drip; that's a v1.5 marketing feature, see `01-specs/pages/_followups.md`)
- Bundle-aware cart (bundles are a single line with sub-items, v2)
- Affiliate link attribution on cart (attribution is captured at order time, not cart time)
- Explicit "Keep both / Use account cart / Use session cart" merge modal on signup — current default is union with auth-wins-on-collision. The modal is a follow-up.

## Open questions for human

- **Resolved in P4.2.** The four open questions in the v1 spec are now closed:
  - Anon cart storage: HTTP-only signed `uthena_anon_cart` cookie (HMAC-SHA256, 14-day TTL). Cookie wins over localStorage for cross-tab persistence + JS invisibility.
  - Anon-to-auth merge policy: union respecting `(product_id, license)` with auth-wins-on-collision. The recommended "Keep both? [Keep both] [Use account cart] [Use session cart]" modal is deferred to a follow-up; the union default is what most commerce sites do and what users expect.
  - `cart_items` table schema: shipped in PH01 migration `0001_initial.sql` (matches the proposed shape, with `status` added for soft-delete + the RLS policy `cart_items_self_all`).
  - Reconciliation: every "Add to cart" action calls `addToCartAction` (the single server action), the nav badge uses `getCartCount()` on the layout, the CartDrawer (P4.1) is the global entry point.

- **P4.6** — Cart abandonment recovery. New cron `04-platform/ci/scripts/cron/detect-abandoned-carts.ts` (script: `pnpm cron:detect-abandoned-carts`, env-gated on `NEXT_PUBLIC_SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY`, fails closed if either is missing). The cron runs the existing `CART_IDLE_DAYS_BEFORE_ABANDONMENT = 25` boundary from P4.3's `cartExpiration.ts` (the single source of truth for the abandonment threshold; a future change to the warn / expiry / abandonment windows lives in one place). Detection is a single `UPDATE cart_items SET status='abandoned' WHERE status='active' AND updated_at < cutoff RETURNING user_id, product_id, license, quantity, updated_at` (PostgREST chain matches the `cart_items_active_updated_idx` index from migration 0024 — O(active + old) index range scan, no separate SELECT). Aggregation: a separate `product_pricing` read builds a `Map<product_id, unit_price_cents>` using the minimum active tier per product as a conservative undercount (defensive against missing tier history; the per-(product, license) join would need a historical pricing table that P19.16 will add). Aggregation lives in `02-features/cart/cartAbandonment.ts` as pure functions (`groupAbandonedRowsByUser` + `buildAbandonedEventProps`) — 8 unit tests cover empty input, single-user, multi-user isolation, unknown product_id defense (no NaN), partial-day rounding (`Math.ceil((now - updated_at) / 1 day)`), and large-cart aggregation. Event firing: per-user event through the new server-side PostHog seam `00-foundations/analytics/posthog-server.ts` (no Node SDK dependency; `fetch` to the EU `/capture/` endpoint; env-gated on `POSTHOG_PROJECT_API_KEY` with `NEXT_PUBLIC_POSTHOG_KEY` fallback for dev parity; schema-validated against `POSTHOG_EVENT_PROPS['cart_abandoned']` before each POST; non-2xx / fetch errors return a typed failure and never throw; 16 unit tests cover env-gated, schema validation, success-path POST body shape, the API-key fallback, host override + trailing-slash handling, and the failure paths). **PII safety**: the user_id is hashed via `hashIdentifierForPosthog` (salt-applied sha256, 32 hex chars, same `AUDIT_HASH_SALT` pattern as `auth/rate-limit.ts`) and the hash is the PostHog `distinct_id` AND the `user_id_hash` prop — no raw UUID ever appears in the PostHog request. **Idempotency**: the `status='active'` filter means a re-run on the same day finds zero rows to flip and zero events to fire. **Cron output**: `abandoned=N affected_users=M would_email=K posthog_fired=F posthog_failed=G cutoff=<ISO> at=<ISO>` — the `would_email=K` line is the seam for STUB-048 (Phase 17 SES adapter + template + per-user "already emailed" log table). When P17 lands, replacing the `console.log` with a `sendEmail(...)` call (plus the `cart_expiration_emails` INSERT) is the full wire-up.
